# 홈랩 기록 발행 가이드

이 프로젝트의 기본 순서는 **Hugo 기술 원문 작성 → 원문 검증과 발행 → 원문을 바탕으로 Velog용 각색 → Velog 게시**입니다. 보안·홈랩·서버와 관련된 공부, 설계, 구축, 운영, 장애 해결, 실험을 이 흐름으로 기록합니다. Hugo가 사실과 변경 이력의 기준이고, Velog는 그 기록을 재미있게 설명하는 이야기입니다.

작업 메모, 명령과 출력, 구성 변경, 질문과 이해한 내용을 재료로 사용합니다. 사용자가 매번 완성된 글을 전달할 필요는 없습니다. 제공된 근거로 글을 구성하고, 빈 사실은 추측해서 채우지 않습니다. 이 규칙은 제공된 작업을 기록하는 기준이며 외부의 모든 활동을 자동 수집하는 기능은 아닙니다.

## 1. 원문을 먼저 작성한다

Hugo의 `content/` 아래 Markdown을 기술 원문으로 사용합니다. 먼저 환경, 목표, 절차, 관찰 결과, 미검증 항목을 구분합니다. 실제 장비 구성, 경력, 성과와 측정값은 근거가 있을 때만 적습니다.

- 한 가지 개념, 설정 방법, 실험 또는 장애 해결은 `content/notes/<slug>/index.md`에 씁니다.
- 설계·선택·구축·검증이 연결된 작업은 `content/projects/<slug>/index.md`에 씁니다.
- 짧은 후속 변경은 같은 글에 날짜와 함께 덧붙입니다. 새로 해결하는 문제가 분명할 때 별도 글로 나눕니다.
- 실행 전 제안, 실제 실행한 절차, 예상 결과, 관찰 결과를 혼합하지 않습니다. 학습만 한 내용은 실습 완료처럼 쓰지 않습니다.

공개 전에는 비밀번호, 토큰, 실명, 공인·사설 주소, 내부 호스트 이름, 장비 식별자, 로그 속 개인 정보를 확인합니다. 예시 값은 `<TOKEN>` 또는 `service.example.internal`처럼 실제 값이 아님을 알 수 있게 씁니다.

이 저장소는 공개되어 있습니다. `draft = true`인 원문과 `stories/`의 초안도 GitHub에서는 읽을 수 있으므로, 민감한 원본 로그나 가리지 않은 캡처를 초안에 커밋하지 않습니다.

## 2. Hugo 기술 문서를 완성한다

프로젝트 글은 문제와 제약, 선택 근거, 구현, 검증, 한계 순서로 씁니다. 노트는 목적과 전제, 절차, 확인, 복구 순서로 씁니다. GitHub 구현 자료가 있다면 특정 커밋이나 릴리스로 연결하고, 독자가 재현하는 데 필요한 버전과 전제 조건을 함께 적습니다.

검증 결과에는 실행한 명령이나 테스트, 판정 기준, 실제 관찰 내용을 포함합니다. 실행하지 않은 테스트는 통과했다고 쓰지 않습니다.

## 3. Velog 이야기를 별도로 쓴다

`stories/`에 같은 주제의 Velog 초안을 만듭니다. 도입은 사건, 질문, 비유 또는 농담으로 시작할 수 있습니다. 다만 실제로 일어나지 않은 장애나 실수를 경험담처럼 만들지 않습니다.

원문과 같은 슬러그의 `stories/<slug>.md`를 사용하고, [Velog 글 틀](templates/velog-story.md)의 `source`에 정확한 Hugo 글 주소를 넣습니다. 기본 구성은 **왜 궁금했는가 → 쉬운 비유 → 실제 원리 → 원문에서 확인한 과정 → 배운 점 → 기술 원문**입니다. 모든 글을 억지로 같은 순서에 맞출 필요는 없습니다.

농담은 도입과 연결에 사용하고, 중요한 명령·조건·복구 절차는 명료하게 씁니다. 가상 대사와 비유를 실제 로그나 경험처럼 보이게 쓰지 않습니다. 성공하지 못한 작업을 성공담으로 바꾸거나 미검증 범위를 생략하지 않습니다.

이야기 글도 그 글만 읽어도 핵심 개념을 이해할 수 있어야 합니다. 마지막에는 “기술 문서”, “구현 자료”처럼 목적이 드러나는 문구로 Hugo와 GitHub를 연결합니다.

## 4. 두 글의 사실을 대조한다

발행 전에 날짜, 버전, 실행 절차, 성공 기준, 결과 수치, 미검증 범위가 일치하는지 비교합니다. 농담이나 비유가 기술적 의미를 바꾸지 않는지도 확인합니다.

기술 원문의 URL을 대표 주소로 유지합니다. 외부 플랫폼에 같은 내용을 재발행할 때는 canonical URL 지원 여부를 발행 시점에 확인합니다. Velog에서 사용자가 지정할 수 있는 canonical 설정이나 공식 공개 발행 API는 확인된 지원 기능으로 전제하지 않습니다. 원문 링크는 사람이 읽는 출처 표시에 도움이 되지만 canonical 설정과 같은 기능은 아닙니다.

## 5. 발행과 수정 기록을 남긴다

발행 순서는 `Hugo 원문 검토 → Hugo 발행 → Velog 각색 검토 → Velog 발행`으로 둡니다. Velog 자동 발행을 전제로 하지 않으며, 초안은 직접 검토한 뒤 게시합니다.

`scripts/export-velog.py`는 이미 작성한 글의 front matter 제거와 자산 URL 변환만 합니다. Hugo 글을 명령에 전달하는 것만으로 재미있는 글로 각색되지는 않습니다. 먼저 별도 이야기를 쓴 뒤 필요한 경우 변환합니다. Hugo의 이미지 URL을 사용할 때는 원문 배포 후 실제 파일이 열리는지도 확인합니다.

Velog 게시 후 실제 URL을 Hugo front matter의 `storyURL`에 추가하면 본문 아래에 이야기 링크가 표시됩니다. 게시 전에는 빈 값으로 둡니다.

사실이 바뀌면 Hugo 원문을 먼저 수정하고 변경 날짜와 이유를 남깁니다. Velog 글의 결론에 영향을 주는 변경이라면 해당 글도 갱신하고 두 링크가 여전히 유효한지 확인합니다.
