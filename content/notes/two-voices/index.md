## 1. 하나의 사실표를 만든다

두 글을 따로 쓰기 전에 확인한 사실을 짧게 정리합니다. 환경, 목표, 실행한 절차, 관찰한 결과, 확인하지 못한 항목을 구분합니다. 두 채널에서 바뀌어도 되는 것은 말투와 구성이고, 바뀌면 안 되는 것은 사실과 검증 범위입니다.

```text
확인한 사실: 실제로 실행하고 결과를 본 내용
해석: 확인한 사실로부터 내린 판단
미검증: 추후 확인이 필요한 내용
비공개: 주소, 계정, 토큰처럼 공개하지 않을 내용
```

## 2. Hugo에는 판단 과정을 쓴다

Hugo 글은 포트폴리오에서 바로 읽힐 수 있게 구성합니다.

1. 해결하려던 문제와 제약
2. 후보와 선택 근거
3. 구현 또는 실험 절차
4. 성공 기준과 확인 결과
5. 한계와 다음 과제

설정 예제나 스크립트가 있다면 [GitHub](https://github.com/jsjk8754) 저장소를 연결합니다. 저장소만 보아도 실행 전제와 민감 정보 대체 방법을 알 수 있게 README를 함께 준비합니다.

## 3. Velog에는 사건과 설명을 쓴다

Velog 글은 “왜 이 문제를 알아야 하는가”를 먼저 보여줍니다. 제목과 도입에는 비유나 가벼운 농담을 쓸 수 있지만, 실패하지 않은 일을 실패담처럼 꾸미거나 측정하지 않은 수치를 만들지 않습니다.

예를 들어 기술 문서의 제목이 `서비스 접근 경로 검증`이라면 이야기 글에서는 `브라우저가 열렸다고 끝난 줄 알았습니다`처럼 독자의 상황을 떠올리게 할 수 있습니다. 본문에서는 DNS, 연결, 인증, 기능 확인을 일상적인 비유로 풀고 마지막에 [기술 문서](https://jsjk8754.github.io/homelab-notes/)와 구현 자료를 연결합니다.

## 4. 발행 전에 서로 대조한다

두 초안에서 버전, 날짜, 성공 조건, 결과가 같은지 확인합니다. Hugo 글이 원문이라면 Velog 글에 원문 링크를 명확히 표시합니다. 플랫폼에서 canonical URL을 직접 지정할 수 있는지는 발행 시점의 지원 여부를 별도로 확인하고, 확인되지 않은 기능을 전제로 자동화하지 않습니다.
